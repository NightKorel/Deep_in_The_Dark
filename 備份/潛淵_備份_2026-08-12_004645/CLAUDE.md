# 給 Claude 的工作規則（潛淵專案）

這個檔案是專案的固定規則。**每次工作前先讀這裡，每次工作都要照這裡做。**
使用者（納可）是程式小白，請用白話說明，不要假設對方懂技術細節。

---

## 🚨 最高鐵則：動工前先看 GitHub（絕對不能跳過）

**每次接手、開始任何工作之前，第一件事就是先看 GitHub（git）上的最新狀態，不能只看本機。**

- 本機資料夾可能是**舊的**（雲端環境會回收、也可能是別條舊分支），GitHub 上的 `main`
  才是遊戲的真身。直接在本機舊版上動手，會改在過時的程式上，跟正式版對不起來。
- 具體要做：先 `git fetch origin main`，確認本機對齊到最新的 `main`（例如
  `git checkout -B <工作分支> origin/main`）再開始，並看一下最近的提交紀錄/分支/PR，
  確認自己是站在最新版上工作。
- **這條沒做，等於白做。任何情況都不例外。**

---

## ⭐ 每次「更新」都必做的三件事

這裡的「更新」＝任何一次改到遊戲內容或檔案的工作。做完主要工作後，依序完成：

### 1. 寫更新日誌
- 檔案：`更新日誌.txt`
- **最新的內容寫在檔案最前面（最上面），不是最後面。**
- 每筆包含：日期、這次做了什麼（用白話）。

### 2. 全部備份
- 執行 `bash scripts/備份.sh` 即可自動完成，它會：
  - 把目前遊戲內容整包複製成一個資料夾，放進 `備份/`。
  - `備份/` 裡**只保留最新 3 個**備份。
  - 第 4 個（含）以上的更舊備份，自動移進 `備份/更舊的/`。
- 若不用腳本手動做，也要遵守上面同樣的規則。

### 3. 更新要求清單
- 檔案：`納可要求清單.txt`
- 使用者給的每個指令都要先登記成一條。
- **還沒做完的，放在檔案最前面（最上面）。**
- **做完的，移到檔案最後面（最下面），並在該條前面標記 `✗`**（表示已完成/已劃掉）。

### 4. 存到 GitHub＋立刻上線（雲端環境特別重要）
- 這是雲端環境，只有 push 到 GitHub 的東西才會保留，本機資料夾會被回收。
- 每完成一個「不會崩」的段落，就**立刻** `git add -A`、commit、push 到 **main**（正式上線 Pages）。
- **納可的明確要求：弄完任何東西都要上線。** 不要積著、也不要只留在開發分支等之後再合併——
  做完不會崩的東西就馬上推 main，讓測試員第一時間玩到。

### 5. 新規則要即時入檔（免得忘記）
- 納可新講的每一條規則、提醒、拍板的決定，都要「當場」補進對應文件，不要只留在對話裡：
  - **工作流程／通則規則** → 寫進這個 `CLAUDE.md`。
  - **遊戲的定案規格（機制、數值、內容規則）** → 寫進 `設計文件/` 裡對應的設計檔。
  - **暫時用不到、但捨不得丟的點子** → 存進 `設計文件/點子庫.txt`（見下方授權說明）。
- 目的：換了新對話、或過一陣子回來，照著文件就能接續，不會忘記或做錯。

## ⭐ 納可的長期授權（可以主動做事）

納可已明確授權，不用每件事都問：

- **看到可以優化／可以做得更好的地方，就直接動手**。只有在「真的不確定納可的意思」時才停下來問。
- **可以自己發想、加入新內容與新細節**（例如她一直想要的**成就系統**——成就可以自己設計、
  自己持續增加更新，不用等她開口）。
- **遺物與隨機事件：想到就可以加**，盡量有趣、這類東西永遠不嫌多；但**不要為了湊數量而做重複、
  雷同的東西**（新的要跟既有的有明顯差異）。
- **不要一次把點子用光**（納可指示）：同一類東西（例如藥水）一次只用一部分，
  規則是**一種材料對應一種產物**（例：一種藥材＝一種藥水，不要一種藥材塞好幾種）。
  想到但這次用不到的點子，先存進 `設計文件/點子庫.txt`，留給之後的圈層／材料用，
  免得太早用完，後面就沒梗了。
- **唯一紅線：不要更動納可明確指定過的東西**——包含既有角色／技能／怪物的設定與數值、劇情台詞、
  已定案的機制與工作流程規則，以及她指定過的功能規格。要改這些才需要先問。
- 主動加的東西一樣遵守下面「穩定版 vs 開發中」規則：先在 `開發中/` 做，完工測好才進根目錄。
- 做完仍要照最上面「每次更新必做的事」：寫日誌、備份、更新要求清單、push 到 main。

## ⭐ 已定案的介面／顯示規則（屬於紅線，別改壞）

這些是納可拍板過的規則，之後做新內容都要遵守：

- **成就一覽防暴雷**：成就列表一律**只顯示成就圖示**；**未解鎖的成就，名字與描述都要遮成「？？？」**
  （圖示當作小小暗示，內容不劇透）。加新成就時照這個規則，別讓成就內容提前曝光。
- **防暴雷原則（通則）**：還沒解鎖的內容，在解鎖前**不能有任何預告**。
  例：賭場入口解鎖前，避難所不顯示入口、不露代幣數字、也不加會暴雷的成就；節點名稱親眼遇到前顯示「？？？」。
- **賭場經濟紅線**（完整規格見 `設計文件/賭場設計.txt`）：
  - **代幣單向**：只能潛晶換代幣，**代幣不能換回潛晶**，代幣只能在賭場花掉。
  - **節點賭場（賭潛晶）有上限**：單注與單局淨贏都要壓在上限內，別讓賭博變成灌爆主貨幣的漏洞。
  - **純技術的賭場遊戲只放代幣場**（避難所），不放賭潛晶的節點場。

## ⭐ 穩定版 vs 開發中（GitHub Pages 上線規則）

GitHub Pages 會把 `main` 分支**根目錄**的內容變成公開可玩的網頁；玩家點的就是這個。

**判斷標準只有一個：這個版本會不會崩潰／壞掉當掉？**（不是「功能有沒有全部做完」）

- **不會崩、跑得起來 → 放根目錄（穩定版）**。就算功能還沒全部做完，只要能正常玩、不會壞，
  就放上去給玩家/測試員玩。
  - 目前玩家都是納可的朋友測試員，所以**作弊選單要保留**（跳教學／通關第一層／全體升等／
    測試第二層等）。
- **可能會崩／正在動刀改到一半 → 暫時放 `開發中/` 資料夾**。等它跑得起來、不會崩，
  再整包複製覆蓋回根目錄成為新的穩定版。
  - `開發中/` 只是「暫存還在弄、可能會壞的東西」的地方；沒有這種東西時，這個資料夾可以不存在
    （要用時再從根目錄複製一份出來改）。
- **推送位置**：直接 commit / push 到 `main`（納可已開好權限），不用另開分支。
- 根目錄有 `.nojekyll`，確保 Pages 原樣提供所有檔案（含中文檔名/資料夾）。

## 專案技術備註

- 純前端遊戲（HTML + CSS + 原生 JavaScript），無框架、無建置流程。
- 直接用瀏覽器打開 `index.html` 就能執行；改完重新整理瀏覽器即可看到結果。
- 檔案結構與系統說明見 `README.md`。
- 改程式前先讀對應檔案開頭的區塊註解（原作者的中文註解很詳細）。
